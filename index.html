Hands-on Course: Build AI Agents and Harness Engineering from Scratch

A hands-on course for engineers: first write an Agent by hand, then polish it into a reliable runtime (Harness). This course is organized around Harness 12-Factor, with each chapter corresponding to a production-grade design principle.

Don't learn Agent as AI; learn it as an unreliable distributed system.

Prerequisites: Python basics, command line, and an LLM API Key (Anthropic Claude recommended; any compatible API works).

Prerequisite: Environment and First API Call

Learning Goal: Set up the environment and understand the minimal structure of an LLM request/response.

Core Content

  • SDK installation and API Key environment variable configuration.
  • Minimal call three elements: system prompt, messages, model parameters.
  • Understanding token billing and length constraints.
  • Difference between streaming and non-streaming responses.

Hands-on Exercises

  1. Write chat.py that receives a sentence from the command line and prints the reply.
  2. Add a multi-turn loop and maintain messages, observing context growth.
Deliverable: A command-line script that can do multi-turn conversation and print token consumption.

Factor 1: Single Agent Loop

The Agent is a state machine: call the model → parse the tool call → execute the tool → feed the result back into context, looping until done.

Example: examples/factor-1

Factor 2: Explicit Tool Contract

Tool descriptions are prompts, parameters are validated inside the tool, and errors return as normal values so the model can keep making decisions.

Example: examples/factor-2

Factor 3: Context Budgeting

Truncation, summarization, and external memory keep long tasks and large tool outputs from blowing up the context window.

Example: examples/factor-3

Factor 4: Knowing When to Stop ★

Define "done" explicitly (a task_done tool plus validation of completion claims), detect loops (repeated tool calls, diminishing returns, similar-content cycles), and trip a circuit breaker when errors cross a threshold.

Example: examples/factor-4 · Reference: nano-agent turn termination policy (pkg/agent/turn_policy.go)

Factor 5: Failure-First Design & Graceful Degradation

Design for failure first — infinite loops, drift, hallucinated calls, partial failures — and degrade gracefully (full success → partial success → safe fallback → graceful failure) instead of crashing.

Example: examples/factor-5

Factor 6: Permission Models

Least privilege by default, with a security–efficiency spectrum: per-call confirmation → session allowlist → auto mode (two-level classifier, fast path for workdir edits, configurable failure policy, 15s timeout) → YOLO — every decision audit-logged.

Example: examples/factor-6 · Reference: nano-agent PERMISSION_AUTO_APPROVAL.md & PERMISSION_POLICY.md

Factor 7: Human-in-the-Loop Gates

Irreversible operations pause at a confirmation gate whose suspended state (full context and trace) is saved and can be resumed later.

Example: examples/factor-7

Factor 8: Plan & Goal Modes

Plan mode explores read-only, produces a plan, and executes only after human approval; goal mode declares a goal with completion criteria and keeps running autonomously until a goal evaluator says they are met.

Example: examples/factor-8 · Reference: nano-agent PLAN_MODE.md + /goal; nano-symphony plan runs & approval gates

Factor 9: Workspace & Artifacts Management

Every task runs in an isolated workspace (git baseline, lifecycle hooks, cleanup policy), and artifacts are the run's persistent output contract — collected, stored, downloadable, and rendered in the UI.

Example: examples/factor-9 · Reference: nano-symphony workspace & unified artifacts management

Factor 10: Composable Agents

Split, dispatch, and aggregate with an orchestrator–worker pattern, isolating and recovering sub-agent failures.

Example: examples/factor-10

Factor 11: Config-Driven & Reproducible Runs

Config is the behavior contract; pin it with workflow templates and checkpoints so any run can be reproduced, replayed, and turned into a regression test.

Example: examples/factor-11

Factor 12: Observability & Continuous Evaluation

Events, metrics, and traces are the data foundation of evaluation — run continuous benchmarks (SWE-bench style) and prioritize whichever factor scores worst.

Example: examples/factor-12

Advanced: Reading Real Harnesses

Learning Goal: Read mature Harness source code with questions in mind and migrate improvements.

Core Content

  • Focus on context management, fault tolerance, permissions, observability, orchestration, config, evaluation.
  • Question-driven reading, not blind full reads.
  • Extract transferable designs and land them in your own Agent.

Hands-on Exercises

  1. Write a deep-reading note for each of 6 questions.
  2. Port at least 1 design to your own Agent.
Deliverable: Source-code deep-reading notes + at least one engineering improvement.

Capstone Project: A Complete Domain Agent

Goal: Combine all Factors to deliver a real, usable domain Agent.
  • Operations / Network direction: parallel diagnosis of multiple devices, writes require confirmation, full trace.
  • Data direction: autonomous query, cleaning, and report generation.
  • Development direction: read codebase, locate bugs, propose fixes.
