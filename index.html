Hands-on Course: Build AI Agents and Harness Engineering from Scratch

A hands-on course for engineers: first write an Agent by hand, then polish it into a reliable runtime (Harness). This course is organized around Harness 12-Factor, with each chapter corresponding to a production-grade design principle.

Don't learn Agent as AI; learn it as an unreliable distributed system.

Prerequisites: Python basics, command line, and an LLM API Key (Anthropic Claude recommended; any compatible API works).

Prerequisite: Environment and First API Call

Learning Goal: Set up the environment and understand the minimal structure of an LLM request/response.

Core Content

  • SDK installation and API Key environment variable configuration.
  • Minimal call three elements: system prompt, messages, model parameters.
  • Understanding token billing and length constraints.
  • Difference between streaming and non-streaming responses.

Hands-on Exercises

  1. Write chat.py that receives a sentence from the command line and prints the reply.
  2. Add a multi-turn loop and maintain messages, observing context growth.
Deliverable: A command-line script that can do multi-turn conversation and print token consumption.

Factor 1: Single Agent Loop

Learning Goal: Implement a tool-equipped REPL loop and understand that Agent is a state machine.

Core Content

  • Call model → Parse tool call → Execute tool → Feed result back into context until done.
  • Tool calling protocol (name/description/parameter schema).
  • Parse tool_use and map to Python functions.
  • Loop terminates when model no longer requests tools.

Hands-on Exercises

  1. Implement the loop in about 100 lines without any framework.
  2. Register the first tool (e.g. run_command / file read / calculator).
  3. Complete a 2-3 step tool-calling task and print each step's action.
Deliverable: A minimal but complete multi-step Agent.

Factor 2: Explicit Tool Contract

Learning Goal: Design tool interfaces that the model uses correctly and reliably.

Core Content

  • Tool description itself is prompt.
  • Parameter validation must be done inside the tool.
  • Return values should help the model continue making decisions.
  • Return errors as normal values; avoid crashing the loop.
  • Tools with side effects must consider idempotency.

Hands-on Exercises

  1. Refactor Factor 1 tools, add parameter validation and friendly errors.
  2. Design a tool with side effects and prevent repeated execution.
  3. Deliberately write a vague description and observe misuse.
Deliverable: A robust tool specification + 2-3 example tools.

Factor 3: Context Budgeting

Learning Goal: Handle the context overflow problem.

Core Content

  • Long tasks and large tool outputs quickly fill the window.
  • Strategies: truncation, summarization, external memory.
  • Tradeoffs between information loss and cost.
  • Distinguish permanent system prompt from dynamically injected information.

Hands-on Exercises

  1. Use an ultra-long output tool to reproduce context overflow.
  2. Implement truncation and threshold summarization strategies.
  3. Compare task quality impact of the two strategies.
Deliverable: An Agent that remains stable under long tasks.

Factor 4: Failure-First Design ★

Learning Goal: Systematically fix infinite loops, drift, hallucinated calls, and partial failures.

Core Content

  • Infinite loop detection and breaking (max steps, repeat detection).
  • Phased goals and self-checks to avoid drift.
  • Intercept unknown tools and abnormal parameters.
  • Partial failure recovery in multi-step tasks.
  • Rate limit / timeout retry and backoff.

Hands-on Exercises

  1. Artificially inject tool errors, rate limits, and unknown tools.
  2. Add Harness guards for each failure type.
  3. Record where a real task drifts and improve.
Deliverable: An Agent that can recover from multiple error types.

Factor 5: Graceful Degradation

Learning Goal: When model or tool fails, the system degrades rather than crashes.

Core Content

  • Degradation strategy pyramid: full success → partial success → safe fallback → graceful failure.
  • When model rambles/refuses, retry with simpler prompt or preset template.
  • When tool is unavailable, return error and let model find another path.
  • Preserve completed portions in multi-step tasks.
  • Give users clear status explanation instead of stack traces.

Hands-on Exercises

  1. Add a "degradation mode" switch to Factor 4's Agent.
  2. Simulate a tool completely unavailable; observe if Agent provides an alternative.
  3. Design a safe fallback response for continuous rambling.
Deliverable: An Agent that degrades rather than crashes in the face of failure.

Factor 6: Least-Privilege Tooling

Learning Goal: Let the Agent safely access the real world.

Core Content

  • Tool allowlist and context-level permission control.
  • Sandbox execution: filesystem and network isolation.
  • Principle of least privilege: read-only by default, explicit authorization for writes.
  • Dangerous operation classification: auto-approve / must confirm / permanently forbidden.

Hands-on Exercises

  1. Implement read-only mode to intercept write operations.
  2. Add confirmation gates to tools with side effects.
  3. Write a permission model checklist.
Deliverable: An Agent with least privilege by default and confirmation for dangerous operations.

Factor 7: Human-in-the-Loop Gates

Learning Goal: Irreversible operations pause for human confirmation; state is recoverable.

Core Content

  • Confirmation gate state machine: running → suspended awaiting → resumed execution → completed.
  • When suspended, save full context and trace; supports exit and later resume.
  • Batch confirmation vs single confirmation.
  • Timeout strategy and audit logs.

Hands-on Exercises

  1. Make confirmation an explicit state inside the loop.
  2. Implement suspend-resume: reload state after program exit and continue execution.
  3. Add timeout and audit events to the confirmation gate.
Deliverable: An Agent with a recoverable human confirmation gate.

Factor 8: Observable by Default

Learning Goal: Make every run visible, replayable, and debuggable.

Core Content

  • Structured events: thinking, tool calling, results, errors, completion.
  • Structured logging: input/output, tokens, time spent.
  • Reproduce and troubleshoot based on trace.
  • Cost observability: tokens, latency, cost.

Hands-on Exercises

  1. Output JSONL event logs.
  2. Implement a simple trace timeline viewer.
  3. Use trace to locate the root cause of a drift.
Deliverable: An Agent whose every run can be traced and replayed.

Factor 9: Reproducible Runs

Learning Goal: Given trace and config, reproduce or locate a failed run.

Core Content

  • Three elements of reproduction: trace + config + seed.
  • Loop paths and tool calls are reproducible; LLM output itself has randomness.
  • Turn failed traces into regression tests.
  • Replay mode: use old trace to replace real calls and quickly verify Harness.

Hands-on Exercises

  1. Save trace + config of a failed run.
  2. Implement replay mode, advancing loop according to the record.
  3. Write a test: given a failed trace, Agent must trigger degradation at step N.
Deliverable: An Agent where failures can be reproduced and fixes can be tested.

Factor 10: Composable Agents

Learning Goal: Upgrade from single Agent to master-sub orchestrator.

Core Content

  • Applicable scenarios: parallel decomposition, context isolation, role-based division.
  • orchestrator-worker pattern: split, dispatch, aggregate.
  • Parallel execution and result merge strategies.
  • Sub-Agent failure isolation and recovery.

Hands-on Exercises

  1. Implement a master Agent that splits tasks into sub-tasks.
  2. Run multiple sub-Agents in parallel and aggregate results.
  3. Reuse Factor 8 trace to support orchestration debugging.
Deliverable: A multi-Agent orchestrator that can execute in parallel and aggregate results.

Factor 11: Config-Driven Behavior

Learning Goal: Externalize model, prompt, tool list, and security policy to configuration.

Core Content

  • What belongs in config: model name, temperature, max_tokens, system prompt, tool list, security policy, etc.
  • Split config by environment: dev / staging / prod.
  • A/B test with different configs.
  • Config changes should trigger automated tests.

Hands-on Exercises

  1. Extract all hardcoded parameters from previous chapters into config.yaml.
  2. Write "aggressive mode" and "conservative mode" configs.
  3. Run the same task with both configs and observe behavioral differences.
Deliverable: A Harness whose behavior is fully driven by configuration.

Factor 12: Continuous Evaluation

Learning Goal: Measure Harness quality with metrics continuously, not just by whether the demo works.

Core Content

  • Core metrics: completion rate, failure rate, recovery rate, average steps/tokens/latency/cost, human-in-the-loop rate.
  • Evaluation dataset: collect real tasks and known failure cases.
  • Batch runner that auto-judges success/failure and outputs a report.
  • Design from metrics backwards: whichever Factor is poor, prioritize improving it.

Hands-on Exercises

  1. Prepare 10-20 representative tasks (including trap cases).
  2. Write evaluate.py to batch-run and record metrics.
  3. After modifying Harness, rerun evaluation and see if key metrics improved.
Deliverable: A Harness that can be quantitatively evaluated and continuously improved.

Advanced: Reading Real Harnesses

Learning Goal: Read mature Harness source code with questions in mind and migrate improvements.

Core Content

  • Focus on context management, fault tolerance, permissions, observability, orchestration, config, evaluation.
  • Question-driven reading, not blind full reads.
  • Extract transferable designs and land them in your own Agent.

Hands-on Exercises

  1. Write a deep-reading note for each of 6 questions.
  2. Port at least 1 design to your own Agent.
Deliverable: Source-code deep-reading notes + at least one engineering improvement.

Capstone Project: A Complete Domain Agent

Goal: Combine all Factors to deliver a real, usable domain Agent.
  • Operations / Network direction: parallel diagnosis of multiple devices, writes require confirmation, full trace.
  • Data direction: autonomous query, cleaning, and report generation.
  • Development direction: read codebase, locate bugs, propose fixes.
